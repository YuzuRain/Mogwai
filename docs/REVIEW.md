## Block 1 · 产品定位与核心循环

**方案**

- 定位:类 OpenRouter 的模型聚合网关 × 宝可梦式养成对战,产品名沿用目录名 **DigMon**。
- 核心循环:托管 Key → 网关调模型(CP 计价)→ 用量采集 → EV/EXP 养成 → 升级抽卡 → 质押 CP 对战 → 胜者赢 CP → 继续调模型。
- 北极星指标:**周活跃对战训练师**(同时用了网关又打了对战的用户)。

**需要拍板**

1. 产品名 DigMon 是否确认?(有 Digimon 商标近似风险,可备选)
2. 首发目标用户:面向开发者(API 调用)还是也覆盖普通聊天用户(自带 Chat UI)?当前设计只做 API + 控制台,**不做 Chat UI**。

**评审结论**:🔧 已裁定(2026-07-25)
**意见**:产品改名 **Mogwai**(已全仓改名)。首发做第三方网关形态(API + 控制台),不做 Chat UI;客户端形态是可替换外壳(未来可能纯 CLI addon),**不变的硬约束是数据与提示词必须回流平台——采集钉在网关层,不依赖任何客户端**(已落 tech-design §1.4 #5)。

## Block 2 · Key 托管与统一网关

**方案**

- OpenAI 兼容协议,模型名 `provider/model`;流式透传。
- 两种模式:**BYOK**(用自己的 Key,平台只收服务费)/ **CP 直购**(走平台 Key 池,按折算价扣 CP)。路由优先 BYOK。
- Key 信封加密(AES-256-GCM + KMS),录入即异步校验,每 6h 巡检,状态机管理。
- provider 不返回 usage 时本地 tokenizer 估算并打 `estimated` 标。

**需要拍板**

1. 首发支持哪些 provider?建议首批:OpenAI、Anthropic、DeepSeek、Qwen(4 家)。
2. ~~平台自营 Key 池(CP 直购)是否 M1 就做?~~(已随 Block 13 记账制裁定连带确定:**首发纯 BYOK**,CP 直购依赖充值,与支付一同 M4 后启用。)

**评审结论**:🔧 已裁定(2026-07-25)
**意见**:首发 provider 5 家:OpenAI、Anthropic、DeepSeek、Qwen、**火山方舟(Seed/豆包)**(已落 tech-design §1.1)。

## Block 3 · CP 折算公式引擎

**方案**

- 三层配置:价格表(官方单价)→ **公式 DSL**(可改结构,非仅改参数)→ 策略覆盖(等级/活动折扣)。
- DSL 用安全表达式引擎(expr-eval / CEL),禁任意代码执行;匹配优先级 model > provider > global。
- 版本化:draft → 沙箱回放 7 天账单 diff → 灰度 → active;每笔扣费记录公式版本 + 变量快照,可审计重算。
- 默认锚定:**1 USD = 1000 CP**;CP 直购 margin ≈ 1.15,BYOK 服务费率 ≈ 5%。

**需要拍板**

1. 锚定汇率 1000 CP/USD 与 margin 1.15 / 服务费 5% 这三个初始值是否 OK?
2. 公式改动是否需要双人审批(运营配置 + 管理员批准)?建议:是。

**评审结论**:✅ 已裁定(2026-07-25)
**意见**:锚定 1 USD = 1000 CP、BYOK 服务费 5% 确认(margin 1.15 随 CP 直购推迟至 M4)。公式改动当前**单人审批即可**(单人团队);双人审批记入长线待办(journal/TODO.md),多人协作后启用。

## Block 4 · 过程数据采集与隐私

**方案**

- LLM 语义数据(prompt/completion/trace)→ **Langfuse 自托管**;行为事件(prompt.edited、regenerated、copied…)→ 自建管道进 ClickHouse;`trace_id` 关联。
- 隐私:prompt 明文存储**默认开启、可一键关闭**;关闭后只留统计特征(长度/结构/语言),EV 计算只依赖统计特征,体验不受影响。明文 30 天滚动删除,入库前 PII 脱敏。

**需要拍板**

1. prompt 明文存储默认「开」还是默认「关」?默认开对调试/客服友好,默认关对信任友好。当前设计:**默认开**。
2. 行为采集需要客户端 SDK 埋点,首发只覆盖自家控制台/H5,第三方接入 API 的用户行为数据缺失(其 EV 只靠调用数据)——接受吗?

**评审结论**:✅ 已裁定(2026-07-25)
**意见**:明文存储**默认开**——数据完整回流是平台核心诉求(与 Block 1 裁定一致)。数据回流/数据资产这一块后续会有更重的专项设计,已记长线待办。第三方 API 用户特征缺失接受,再归一化方案(tech-design §5.2)已覆盖。

## Block 5 · 努力值(EV)六维映射

**方案**

- 六维:HP=粘性时长、攻击=直接指令/一次采纳、防御=纠错恢复、特攻=创意复杂任务、特防=对输出的批判审查、速度=交互节奏。
- 管道:事件 → 小时级特征(ClickHouse)→ 全体分位数归一化 → 权重矩阵(运营可配)→ **每日结算**。
- 宝可梦式约束:单项 252 / 总和 510 / 溢出转 EXP;**每周日全体 EV ×0.98 衰减**。
- 面板 = 种族值(选种族)+ 个体值(注册随机 0~31)+ EV,套宝可梦三代公式。
- 付费道具「营养饮料」定向 +10/瓶,道具加成单项上限 100。

**需要拍板**

1. 周衰减 0.98 会让停用玩家缓慢变弱,是留存钩子也可能招差评——保留还是改为「仅赛季重置」?
2. 个体值(IV)随机会造成出生不平等,是否提供一次「重测 IV」道具?当前设计:不提供。

**评审结论**:🔧 已裁定(2026-07-25)
**意见**:两处改设计:① **取消周衰减**,EV 只增不减,老玩家碾压交给赛季重置(M5 设计);② **IV 改窄幅随机**——总和恒定 126、单项 13~29,随机只决定倾向不决定强弱,不需要重测道具,成长主要靠养成(EV)。均已落 tech-design §5.2/§5.3。

## Block 6 · EXP 与等级

**方案**

- `exp = floor( 0.05 × (in_tok×0.3 + out_tok×1.0)^0.9 )`;次线性压氪。
- 等级曲线:中速经验组 `L³`,满级 100。
- 反刷:单日 EXP 上限 50,000(超出折半);高相似度重复 prompt(SimHash)打折。

**需要拍板**

1. 粗算:日常重度用户(~50 万 token/天)约 1 个月到 40 级左右——这个成长节奏偏快/偏慢?
2. 满级 100 后 token 是否继续产生价值?建议:溢出 EXP 转「赛季币」(M5 再做)。

**评审结论**:🔧 已裁定(2026-07-25)
**意见**:原节奏偏慢,等级曲线由中速组 `L³` 改为**中速偏慢组** `1.2L³ − 15L² + 100L − 140`,前 20 级显著加速、总量不变(已落 tech-design §6.2)。满级溢出转赛季币维持 M5 再做。

## Block 7 · 技能池与抽卡

**方案**

- 技能:属性(参与克制表)+ 物理/特殊/变化 + 威力/命中/PP + 稀有度 N/R/SR/UR;**最多装备 4 个**。
- 概率:N 60% / R 30% / SR 9% / UR 1%;十连保 SR,80 抽硬保底 UR,50 抽后软保底;重复转碎片。
- 随机数服务端 HMAC 种子,可审计不可预测;概率公示。
- **抽卡券只来自升级/活动,不直售**;CP 只能买养成道具。

**需要拍板**

1. 首发技能池规模?建议 60 个(N 24 / R 20 / SR 12 / UR 4)。
2. 技能属性体系:直接用宝可梦 18 属性,还是自创 AI 主题属性(代码系/创意系/审查系…)?当前设计倾向**自创 8~10 个属性**,与 EV 风格呼应。

**评审结论**:🔧 已裁定(2026-07-25)
**意见**:首发技能池缩到 **40 个**(N 16 / R 13 / SR 8 / UR 3),先保质量。属性体系**先用宝可梦 18 属性**(平衡性现成),自创属性放到 M3 技能模块设计时再评估——此类模块内数值设计不再前置拍板(用户明确:非阻塞项不提前决策)。已落 tech-design §7.1。

## Block 8 · 匹配系统

**方案**

- Glicko-2 评分(内部)+ 赛季段位(展示);质押档位 100 / 500 / 2000 CP,同档撮合。
- 匹配窗口 |Δrating| < 100 + 15×等待秒,逐步放宽;综合战力差阈值兜底(战力 = 0.4 等级 + 0.35 EV + 0.25 技能)。
- 90 秒匹配不到 → **幽灵队伍**练习赛(真实玩家快照 AI 代打),~~质押减半、奖励平台奖池出~~(2026-07-25 随记账制裁定修改:无经济转移,担保全额解锁)。
- 反喂分:同 IP/设备/高频互战禁撮合。

**需要拍板**

1. 质押三档数值是否合理?(参照:1000 CP ≈ 1 USD,即约 $0.1 / $0.5 / $2 一场)
2. 幽灵队伍战斗是否明确告知玩家对手是 AI?建议:**明确告知**(信任 > 数据)。

**评审结论**:✅ 方案通过(2026-07-25)
**意见**:框架(Glicko-2 + 同档撮合 + 幽灵练习赛明确标注)通过;质押档位等具体数值**定于 M4 匹配模块设计时**,不前置拍板。

## Block 9 · 战斗系统

**方案**

- **回合制自动战斗**:赛前配技能 + 策略倾向(激进/均衡/保守),战斗无实时操作;30 回合未分胜负按剩余 HP% 判胜。
- 服务端权威 + 确定性模拟(种子化 PRNG),客户端只播动画;回放 = 重新模拟,争议可复盘。
- 伤害公式完整仿宝可梦(等级/威力/攻防比 + STAB 1.5 + 克制表 + 1/16 暴击 + 0.85~1.0 随机)。

**需要拍板**

1. 自动战斗(无操作)vs 半自动(每回合限时选技能)?自动适合 H5 短平快、可异步战斗;半自动策略性强但要求双方在线。当前设计:**全自动**。
2. 单场战斗动画时长目标?建议 ≤ 60 秒,可跳过直接看结果。

**评审结论**:✅ 方案通过(2026-07-25)
**意见**:全自动战斗 + 确定性模拟框架通过;动画时长等表现细节**定于 M3 战斗模块设计时**。

## Block 10 · 结算与经济闸门

> ⚠️ 2026-07-25 部分被 Block 13 裁定覆盖:改为**纯记账制**——平台不抽成(rake 取消)、不托管;败方损失记为对胜方的债务,以托管 Key 承担胜方 token 消耗实物清偿。以下保留供比对。

**方案**

- 败方损失 = 质押 × **30%**;~~平台抽成损失的 10%;平局各扣 2%~~(已改:损失全额记为债务归胜方,平局无转移)。复式账本、battle_id 幂等、10 分钟超时自动全额解锁。
- 闸门:每日新增债务上限 = 担保额度 20%;新手前 10 场损失减半;**CP 不可提现**(合规红线)。

**需要拍板**

1. loss_rate 30% 手感:输一场 500 档 = 损失 150 CP ≈ $0.15。太温和会缺刺激,太狠会劝退——初始值认可吗?
2. ~~BYOK 用户质押来源与送 CP~~(已由 Block 13 裁定覆盖:入场券 = 托管 Key 担保额度,不赠送、不充值)。

**评审结论**:🔧 已裁定(2026-07-25)
**意见**:`loss_rate` 由 30% 调低为 **20%**(降低劝退风险,已落 tech-design §10.2 并入对战合约默认值)。其余按 Block 13 记账制执行。

## Block 11 · 技术架构

**方案**

- **模块化单体(NestJS)+ 独立网关(Fastify)**,TypeScript 全栈,Next.js 前端;pnpm + Turborepo monorepo。
- 存储:PostgreSQL(账本强一致)+ Redis(队列/Streams)+ ClickHouse(事件特征)+ Langfuse 自托管。
- 关键隔离:网关只依赖 Redis + KMS,core-app 全挂不影响 AI 代理主链路;模块间禁止跨表访问,跨进程只走事件总线。
- 两个纯函数核心包:`battle-core`(确定性战斗,前后端同构)、`formula-engine`(折算 DSL)。

**需要拍板**

1. TS 全栈是否匹配团队技术栈?若团队主力是 Go/Python 需要现在说。
2. 事件总线 Redis Streams 起步、规模化再迁 Kafka——认可这个偷懒吗?

**评审结论**:✅ 已裁定(2026-07-25)
**意见**:TS 全栈确认。选型依据是「只选对的,不选会的」(团队单人,主力 C++/C):battle-core 要求前后端同构的确定性模拟,仅 TS 可零成本满足;zod/drizzle/BullMQ/better-auth 契约生态成熟;服务端不是性能瓶颈(瓶颈在 LLM 上游),Rust 无对应收益;网关性能敏感部分已由 LiteLLM 承担,有 Bifrost 替换预案。Redis Streams 起步认可。

## Block 12 · 路线图与优先级

**方案**

| M1 | 网关 + Key 托管 + 公式引擎 + 账本 + 控制台 | 4 周 |

## Block 13 · BYOK 用户的 CP 冷启动(2026-07-25 架构评审新增)

**问题**

支付/充值暂缓(架构 A3 #26)+ BYOK 每笔调用收服务费(CP 计价)→ M1 的 BYOK 用户第一天就没有 CP 可扣服务费,也没有 CP 可质押对战,主循环起不来。

**候选方案**

1. ~~注册赠送一次性 CP~~;
2. ~~M1~M3 阶段 BYOK 免服务费~~;
3. ~~允许服务费负余额记账~~。

**评审结论**:✅ 已裁定(2026-07-25)——**问题前提被推翻,改为纯记账制**。
**意见**:不赠送、不托管。无质押能力就不能进对战(入场券 = 托管 Key 担保额度)。平台只负责记账:败方在账本上背负对胜方的 CP 债务,以自己托管的 Key 为胜方承担等值 token 消耗清偿;平台不抽取赌注,收入只来自服务费。已落入 tech-design §3.5/§10 与 architecture A4/B5.2。
